# 函数与异步流程

新建或修改函数时，先明确用途、输入输出、实际调用方和资源责任。拆分后每部分仍能说明职责，避免只为缩短函数增加多层转交。

## 条件与分支

合并重复条件和同义判断，减少多层 `if` 与嵌套三元表达式。合理使用提前返回，让正常流程顺着读；按同一状态分类时可用 `switch`，分支覆盖所有合法状态。不把换一种语法本身当成优化。

错误分类、默认原因等相同规则维护一处，调用方再转换为自己的结果或提示。判断优先级、字段缺失、空值和原文案按契约保留，不因整理条件改变结果。

异步等待前后的相同判断可能保护不同阶段。身份、目标或状态可能在等待中变化时，后续阶段仍需检查，不能仅因表达式重复就合并删除。

## 依赖与执行顺序

函数只接收实际需要的参数和能力，避免把整个页面、业务对象或上下文传入只用少量字段的逻辑。纯计算保持同步；需要等待的操作按实际依赖表达，不为统一形式增加 `async` 或无意义的 Promise 包装。

独立且允许并行的任务一起启动，需要前一步结果的任务顺序执行。改变并行方式前，核对共享状态、限流和服务约束；聚合 Promise 拒绝不代表其余工作自动停止，已启动任务仍需按约定收尾。

修改回调、`async/await` 或 Promise 链时，同时检查错误如何传播、结果何时交付。同步检查移入异步函数可能把抛错变为 Promise 拒绝；新增 `.then` 等交接也可能改变完成和取消的先后。已有时序有实际用途时保留，并在代码旁说明原因。

## 结果与资源收尾

界面呈现、执行资格、资源占用和持久化各自遵循所属生命周期。处理暂停、隐藏、关闭、销毁或重建时，明确哪些状态保留、哪些执行停止及哪些资源释放；保留界面不延长已失效的执行资格，结束展示也不撤销已交付的事实。恢复根据仍有效的内存实例或持久事实进行，不把所有生命周期事件都实现为销毁后重建。

- 每轮操作绑定原实例、身份和目标。取消、卸载或归属失效后，旧结果和旧轮清理不能影响新操作。
- 取消等待、底层停止、业务完成和资源释放分别判断。等待结束不证明底层已经停止，也不代表已完成的业务可以撤销。
- 已确认或已交付的结果保留原事实，随后发生的取消不改写成功。仍在等待的操作按所属契约交付取消或其他结果。
- 一次性操作只完成一次；重复回调、取消或销毁安全处理。移除已结束操作的监听和记录，借用或已交给他方的资源按原责任释放。

恢复与重试依据操作契约区分读取、可重复计算和有副作用的写入，核对原结果是否已确认、原请求是否仍有效，以及幂等、核实和取消能力。新建执行或延续原执行由这些条件决定，不能把某一场景的重试方式推广到所有操作；旧结果与收尾始终保留原归属。

## 错误与诊断

正常失败、取消和程序异常按所属契约处理，不用空数据或成功结果隐藏错误。已有公共错误分类直接复用，第三方错误码和异常细节放在接入代码中，不让每个业务调用方重新解释。

按契约区分核心操作与附属处理的结果。核心结果已确认后，附属处理失败不能将其改为失败、引导重复执行或阻断无依赖关系的操作。决定阻断、用户提示、日志及恢复措施时，核对实际影响和用户需要采取的动作；属于成功条件、数据完整性或重复提交保护的步骤继续保留，不能仅因发生在本地或存储层就归为可忽略失败。

异常进入后续回调或 Promise 拒绝分支时，调用归属可能已变化；按该操作的规则重新判断能否交付结果。新增的有效性检查自身抛错时，也要保留必要的失败交付和清理，避免兜底再次抛错后一直等待。

### 故障证据与记录边界

诊断记录应能关联一次故障的操作、阶段、关键判断、依赖和结果。日志与功能同步设计，运行前配置必要采集；定位不能依赖故障发生后临时补采。证据不足时区分已知事实与未明原因，通用失败码不能作为根因。

| 场景 | 应保留的证据 |
|---|---|
| 外部服务、模型、设备、数据库或文件调用 | 原操作关联、阶段、耗时与结果，以及安全的状态、错误类别和原始码；关键调用的开始与结束可衔接 |
| 解码、转换、校验或结果丢弃 | 使用的契约或规则、失败字段或项目位置、具体受控原因与处理结果；包装和回退前保留底层原因 |
| 持久化、异步交接、取消后的收尾 | 已交付与未确认的事实、原实例／身份／操作、必要的保存或释放失败；不将迟到事件记给新操作 |
| 降级、恢复、去重和重试 | 采用原因、受影响阶段和恢复结果，能还原为什么走了该分支；重复故障压缩后仍保留原因变化 |
| 纯取值、无副作用计算、样式、每次渲染、正常取消或合法无匹配 | 不机械新增日志；确需说明关键业务决定时记录受控摘要，不默认提升为错误 |

诊断按职责分为主日志、操作关联和必要的大内容附日志，不要求每处变更同时产生三类记录。主日志回答阶段、结果和安全原因；跨边界或异步操作需要关联贯穿调用、任务和交接；模型输入输出、响应或校验上下文过大且影响定位时，按类别与受控策略保留在私有附日志中，主日志只存索引、摘要和保存状态。策略在运行前按诊断需要确定，不以事后开启采集替代本应保留的失败证据；没有定位用途的内容不采集。

最有上下文的一层记录详细原因，其他层保留关联和新增决策，不重复整段异常。级别表达影响：不可继续的技术或契约故障用错误，可恢复依赖失败或降级用警告，关键事实和恢复用信息，高频细节按调试策略。已有证据足够时复用，不能为“覆盖”在每个函数或 catch 加打印。

复用工程公共日志入口及治理能力，字段按契约投影、脱敏并限制大小。主日志和附日志都排除密钥、令牌及认证信息；正文或业务数据仅在定位确有必要且符合访问约束时进入受控附日志。附日志须约定私有目录、读取权限、身份隔离、保留时间、容量、截断与清理；缺失、关闭、采样、截断或保存失败要能识别。日志失败不得改变原返回、异常传播、重试、事务或资源清理，也不递归写入失败通道。

验证时从一次代表性失败产生的记录还原调用与决策，检查关联、原因、级别、敏感信息和实际采用的附日志索引；覆盖取消、迟到和诊断存储失败。必要历史用于解释当时事实，不表示业务成功，也不替代业务权威数据。

## 函数与逻辑注释

新增和修改代码时，在公共入口、工厂和关键内部函数旁说明名称与类型无法表达的约定，包括使用限制、何时交付结果、谁负责取消和释放资源。关键判断及异常分支说明为什么保留这项检查、为什么采用这个顺序。

注释与代码一起维护，删除过期说明，不逐行翻译实现。显而易见的简单操作不强制增加模板注释；重要约定同时保留在实现附近的契约说明中。

## 按影响验证

检查实际功能和相关调用方。新功能按需求验证，修复问题先复现，重构对照原有行为；从本次影响中选择检查项：

- 返回值、字段缺失与默认值，抛错和 Promise 拒绝是否仍按约定处理。
- 校验、请求启动、状态更新和结果交付的先后，失败后不应发生的操作。
- 多请求、共享取消信号、不同等待阶段的销毁、乱序完成和迟到回执。
- 原实例与新实例隔离，重复收尾、监听清理及资源归属。
- 临时更新与持久事实的保存范围，附属失败不改写核心结果，以及必要前置失败时不启动后续操作。
- 异常兜底、有效性检查及日志自身失败时，调用能否正确结束并保留必要诊断。

运行真实实现和调用方，在必要的外部依赖处替换。竞争场景用可控 Promise 或事件安排先后，不靠任意延时碰运气；测试预期来自需求和契约。性能判断依据测量，分别定位计算、渲染、序列化、存储和外部等待，调用或更新次数不直接等于实际耗时；优化后核对有效更新及业务约束。

交付时对应目标、源码修订、配置、产物与实际运行内容核对证据。静态检查、自动化、构建、安装、启动、连通和业务验收按实际涉及的层级分别报告，结论限于已取得的证据。配置文件正确或进程存活不单独证明目标内容已生效；恢复失效环节时复用仍有效的结果，未受影响的步骤不无故重做。普通局部修改不因此启动无关部署或完整业务验收。

## 语言依据

上述规则按实际语言应用，不要求所有语言使用 JavaScript 写法。JavaScript 的异步函数体抛错会使返回的 Promise 拒绝，见 [ECMAScript AsyncBlockStart](https://tc39.es/ecma262/multipage/control-abstraction-objects.html#sec-asyncblockstart)；其他语言按采用版本的规范核对错误和调度语义。
