# 仓库设置与分支保护

先核对当前仓库、默认分支与真实注册的检查，再调整远端。模板包含合并策略、安全设置和 RN 检查名称；工程未采用此基线时，不把模板直接套到其他技术栈。

## 已采用 RN 交付工具的工程

以下 `setup-repo.sh` 使用 `uni-github-delivery/rn` 采用记录；无记录时退回内置 RN 检查模板，并要求可直接推送的发布 Integration。它不是任意技术栈或无自动发布仓库的通用初始化器。

```sh
bash scripts/setup-repo.sh example/widget --target-path /path/to/widget --check
```

`--check` 只读。缺权限、必需检查尚未注册、多个同名 ruleset 或无法取得关键配置时失败，不先写远端再猜结果。应用模式不带 `--check`，需要本次任务明确授权，并在修改后回读核对。

发布 App 必须属于目标工程已批准的发布身份。已有 bypass actors、额外检查和非受管规则保留；新建保护且缺少可直接推送的发布 Integration 时，明确提供真实 App ID：

```sh
bash scripts/setup-repo.sh example/widget --target-path /path/to/widget --release-app-id 123456 --check
```

核对 App 安装范围、仓库变量和 private key 来源后，再执行获准的应用操作。工具不创建 App、不搬运私钥，不把模板作者的 App ID 赋给其他项目。已有同 ID 的受限 bypass 不能自动放宽。

组织的仓库设置和安全策略从目标工程 `.github/organization.json` 取得，省略项保留远端现状。必需检查从工程已采用的 `.github/delivery.json` 取得，既有远端额外检查继续保留。安全功能变化须在本次授权内，不因技能安装而修改远端。

## 其他技术栈与无自动发布仓库

使用工程已有配置工具；没有适用工具时，使用已登录的 `gh api` 完成以下核对与获准修改。分支保护不以发布自动化为前置，没有发布任务就不需要创建发布 App 或配置其绕过权限。

1. 读取目标仓库元数据与管理权限、默认分支、传统保护、包含父级的 ruleset，以及目标分支的有效规则。传统保护返回“Branch not protected”仍须检查 ruleset；403、超时或无法读取不能当作未配置。
2. 从项目约定确定允许的合并方式、分支删除行为、PR 和 CI 要求。必需检查取实际 Actions 作业或状态记录中的名称，并核实 PR 会触发它们；不能填入 RN 默认作业或未经注册的名称。
3. 准备实际差异后，按授权 PATCH `repos/{owner}/{repo}`，并通过 `repos/{owner}/{repo}/rulesets` 创建或更新本项目管理的规则。保留非受管规则、已有更强约束、额外检查和既有 bypass；多个同名规则先核对归属。新规则未采用获准的例外身份时使用空 bypass，不默认豁免管理员、个人账号或借用其他项目的发布 App。
4. 回读仓库设置、规则的启用状态、匹配分支、必需检查及 bypass，再通过 `repos/{owner}/{repo}/rules/branches/{branch}` 确认有效规则。与预期不一致即报告未完成，不以 API 写入成功替代生效核验。

常见的 PR 流程约定包括必须经 PR、必需 CI 通过、禁止非快进更新与删除目标分支；Squash 和合并后自动删除源分支属于仓库合并设置。具体取值来自项目，而非由平台类型推定。规则检查不需要向受保护主线写入试探提交；未做真实拒绝测试时，不宣称已观察到推送被拦截。

组织默认贡献/安全文件的自动继承仍是 GitHub `.github` 特殊仓库功能；它与本技能的交付标准分开。保留该功能的组织可继续维护默认文件，不因此让 CI 依赖旧工程标准仓。
