# 代码组织与实现规范

适用于所有代码开发、维护和审查工作。遵循明确需求和已有约定，保留未要求改变的行为；语言、框架和构建工具的具体要求从当前项目取得。

## 调整依据与确认

开始或接续任务时，核对最新目标、有效契约、明确排除项和已撤回意见。询问现状或只读审查时，交付实际行为或发现。同一请求另有修改要求时，说明拟改位置、行为变化和影响入口，按已确认范围推进。

提出或采纳改法前，沿相关入口核对原行为的用途、状态归属、实际消费者及影响。某处没有采用预想的做法时，先查目标是否已由其他路径满足。已有能力满足目标就沿用。建议变更时，说明现有行为与目标的具体差距及依据，优先在所属实现补齐，必要时新增或替换。复用仍有效的证据，自行从代码、契约或日志补查必要事实。证据只支持推测时，说明还需核实什么。

发现尚未确认的事实偏差、目标不符或其他有效行为受影响，或需新增范围外服务、权限或部署依赖时，说明具体依据、后果和需要用户决定的取舍，先请用户确认该部分。可以给出建议，不替用户选定、不先改后问，也不把技术偏好当作拒绝理由。用户了解影响后明确确认变更，就按新决定推进并更新相关契约和验证，不再用旧决定反复确认；不依赖该决定的工作继续。

依据充分且没有实质疑点的修改直接在授权内执行；纯偏好和已有契约下的等价调整不追加确认或完整设计流程。现有代码不自动构成保留理由，新增或保留兼容、迁移和回退，以及删除或替换实现，都须核对有效需求、实际消费者和数据保护责任。保留未要求改变的行为和已有工作区修改，来源不明的差异先核对归属。替换后迁移调用及相关类型、配置、文档和测试，清理确认失效的实现。

## 基本要求

1. **分清职责。** 不同职责合理拆分，相关逻辑放在一起。名称说明用途，参数只传实际需要的内容。
2. **写清判断。** 合并重复条件，减少多层 `if` 和嵌套三元表达式。合理使用提前返回、`switch` 或函数拆分，保留各阶段必要的校验。
3. **合理复用。** 相同功能和规则统一维护。提取公共入口前核对业务、平台和实例差异，私有实现留在所属模块。公共能力不依赖具体使用者，第三方接口和 SDK 的细节由接入代码处理。
4. **明确类型。** 写清每种状态允许哪些字段，让类型检查拦住错误组合。复用已有公共类型和 Schema，保留外部数据校验。
5. **管好异步操作。** 结果和清理绑定所属实例、身份与操作；失效操作不能影响仍有效的操作，取消不能覆盖已交付的成功。多个仍有效的操作按既有契约各自完成，不默认后发替代先发。处理好重复调用和资源清理，调整异步写法时检查执行顺序。
6. **正确处理错误。** 按约定交付失败、取消和异常，区分核心操作与附属处理的结果，按实际影响决定阻断、提示和恢复。出错后完成必要清理，避免一直等待；按实际失败边界保留可定位一次问题的证据，记录与不记录的条件见[错误与诊断](references/functions-and-async.md#错误与诊断)，诊断失败不影响原流程。
7. **补齐必要注释。** 新增和修改代码时，说明重要函数的用途、使用限制，以及谁负责创建和清理资源。关键判断和异步逻辑说明为什么这样处理，注释随代码同步更新。
8. **按改动范围验证。** 检查功能是否符合需求、相关调用是否仍然正确，覆盖受影响的异常和边界。修复先复现，重构对比前后行为，同时核对受影响的动态注册、路由、生成入口及权限、身份与数据保护。分别报告静态检查、运行验证和未验证项。
