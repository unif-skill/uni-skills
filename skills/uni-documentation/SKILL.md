# 编写与维护工程文档

从读者要完成的任务出发，定位 README、指南、API、源码注释或文档站中的现有条目。按读者使用入口更新受影响内容，用真实接口、命令和生成结果核对文字。

源码中的方法契约与实现注释按[源码注释](references/source-comments.md)处理，采用当前语言和工具的格式，不因加载本技能批量补注释。文档内容按下文处理；涉及站点、导航、页面展示、文档生成或构建时，另读[文档站](references/website.md)。普通文字修改不要求改建网站。

## 编写与整理

1. 确定读者、任务与文档范围，定位目标信息在现有正文、条目及直接引用中的位置。按[增量维护](references/writing.md#增量维护)判断应保留、改写、合并或新增，再按[文档类型](references/content-types.md)组织所需信息。
2. 以现行需求、有效契约和文档范围为依据，用公开接口、配置和相关实现核对事实。区分目标设计、已实现能力、支持声明与验证结果；材料冲突时指出具体差异，不改写正确契约来迎合实现。
3. 按[表达与审校](references/writing.md)选择与信息关系相符的呈现方式，说明用途、操作和结果，必要条件在操作前可见。相关细节放在所属章节并链接，不在每份文档重复整段说明。
4. 生成文档从来源修改后重新生成。按[审校与验证](references/writing.md#审校与验证)检查差异、入口链接和实际呈现，报告已执行的验证范围。

## 信息完整性

精简删除重复叙述和无助于使用的过程说明，同时保留影响正确使用的默认值、权限、依赖、平台限制、错误、取消、并发及资源处理要求。未发生的验证不能写成既成事实。

API、命令、协议字段和代码标识保持准确。示例使用真实公开接口，给出所需上下文；资料缺少签名、参数或成功条件时先核查，不自行补造。业务变化、依赖升级、发布或部署按各自任务范围处理。

已有计划、设计、有效契约和必要验收结论继续保留。历史材料保留原有时间与语境；已失效或撤回结论标明状态，不继续作为当前指引。个人设备、账号和临时运行记录放在仓库外。许可证、署名与引用按其原文及维护要求保留。
