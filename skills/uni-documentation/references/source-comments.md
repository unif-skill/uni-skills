# 源码注释

先核对读者需要、代码职责、有效契约及现有文档工具。文档注释帮助调用者正确使用一个入口；实现注释帮助维护者理解代码中不直观的原因、约束或时序。两者可以同时需要，但不互相替代，也不按方法数量或注释覆盖率机械补齐。

## 方法与入口文档

公共入口、工厂和重要内部方法若存在仅凭名称与类型看不出的契约，应在其维护源附近说明职责、输入约束、返回含义、重要副作用、错误及生命周期责任。工厂尤其说明创建的是何种实例或资源、是否共享、由谁关闭；内部方法按跨越的职责与误用风险判断，不因 private 就省略重要约束，也不要求每个私有辅助都写完整标签。

按实际需要选择信息，不把下列内容变成必填模板：

- 输入的单位、有效范围、前提和所有权；输出的含义、缺省或空结果及资源交接。
- 同步抛错与异步拒绝的条件；返回时和实际完成时的区别。
- 可观察副作用、并发限制、取消、回调时序和清理责任。

不复述已明确的类型、函数名或逐项赋值；显而易见的访问器与纯函数可不加说明。已有文档准确时仅补实际缺口；注释与实现冲突应先核实契约，不能把缺陷写成新标准。生成 API 文档从公开类型或注释维护源更新，不手工维护第二份相同说明。

## 实现注释

在相关代码附近解释非直观原因，例如为何必须先校验再发请求、为何某处不能并行、为何取消后仍要等释放信号。说明被保护的约束和适用条件，避免把当次修复过程、临时讨论或猜测写成永久规则。代码已经直接表达“做什么”时不逐行翻译；能通过准确命名和合理结构澄清的内容先改善代码。修改逻辑时同步核对相关注释，清理已失效说明。

## 格式与官方依据

沿用项目采用的语言、版本和文档生成器。JavaScript 可使用 [JSDoc](https://jsdoc.app/about-getting-started)，TypeScript 项目采用 TSDoc 时可按其 [@param](https://tsdoc.org/pages/tags/param/)、[@returns](https://tsdoc.org/pages/tags/returns/)、[@remarks](https://tsdoc.org/pages/tags/remarks/) 与 [@throws](https://tsdoc.org/pages/tags/throws/) 表达实际信息。标签只在提供有用语义且工具支持时采用，不补无意义的空标签，也不将 Promise 拒绝误写成同步抛错。TypeScript 文件已有类型语法，不照搬 JavaScript 的类型注解标签；支持范围见 [TypeScript JSDoc Reference](https://www.typescriptlang.org/docs/handbook/jsdoc-supported-types.html)。

Python 采用项目 docstring 风格并参考 [PEP 257](https://peps.python.org/pep-0257/)；其他语言沿用其文档约定，不强制 JSDoc/TSDoc。官方资料规定各自语法与用途，本技能关于何时需要注释、信息取舍与避免重复的规则属于工程维护建议。必要时运行项目已有文档解析、lint 或生成检查，并核对实际输出；格式通过不能证明契约描述正确。
