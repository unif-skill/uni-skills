# 按文档用途组织内容

统一写作要求，不统一所有文档的标题或长度。先沿用项目有效的信息结构，缺少必要入口时再补充。

| 文档 | 应提供的内容 |
|---|---|
| 项目或库 README | 简短用途、适用范围、必要准备、安装与最小用法、详情入口 |
| 安装和接入指南 | 前置条件、依赖与配置、按顺序执行的操作、预期结果及必要排障 |
| API 参考 | 用途、签名、参数与默认值、返回值、错误和实际影响使用的边界 |
| 脚本或 CLI 说明 | 命令目的、输入、默认行为、示例、写入或删除影响、退出码与排障位置 |
| 开发与贡献指南 | 源码和规则入口、开发配置、检查与构建、实际贡献和交付流程 |
| 设计与架构 | 当前目标、职责、有效契约、关键约束、必要设计理由及待确认事项 |
| 实施计划与验收 | 已确认范围、执行安排或验收条件、实际结论及其证据边界 |
| Agent 入口 | 适用任务、技能名称、项目规范来源及少量项目特有约束 |
| 包、仓库与网站描述 | 名称、类别、核心用途；对应当前能力与支持范围 |

## README 与详细指南

README 按初次接入顺序提供用途与范围、必要准备、安装、最小用法和详情入口。最小示例展示最常见的真实调用。库按实际分发提供文档、API、示例、包和许可入口；脚本或应用使用自己的安装与运行入口，不套 npm 结构。

详细依赖范围、平台配置、补丁维护、开发和验证步骤放对应指南。直接影响能否使用的条件在 README 简短可见，并链接详情。安装命令保持必要且准确；文档提炼不删除必需的 peer、权限或重建步骤，也不在入口重复全部配置。

区分三种版本信息：项目声明的支持范围、实际开发或测试环境、补丁或外部服务的精确适用版本。各自依据 manifest、当前接入契约或真实验证；验证过一个组合不代表所有消费者都要锁定它，也不代表其他版本均已验证。

## API 与示例

以读者操作描述接口，例如“下载文件到指定目录”，再说明参数和结果。表格用于比较字段、类型、默认值和条件；简单接口可用短段落。已有公开类型或生成链时保持同源，不复制整份 Schema 手工维护。

异步接口说明调用返回与实际操作结束的关系；取消是否停止底层工作、何时能删除文件等按真实契约准确表达。需要调用方处理的错误、状态和资源事项放在对应 API 附近。

最小可运行示例包含真实导入及必要初始化，输出与当前接口一致。只展示局部片段时说明前提和省略内容；未提供的权限、凭证、回调或环境由谁提供应可找到。不能通过虚构字段、包名或方法让示例看似完整。

示例、平台演示和测试说明保留真实支持边界。截图、模拟数据或浏览器演示能说明什么就描述什么，不将其写成原生功能已运行的证明。

## 脚本、工程与设计资料

命令按前置条件和执行顺序组织。脚本区分默认预览与实际修改，明确作用路径、必要输入、部分失败与退出状态；示例使用可理解的占位值，不嵌入个人目录或凭据。

开发文档说明当前工程如何运行和维护。模板、组织标准和通用技能通过明确入口引用；详细规则由所属来源维护，AGENTS.md 保持简短，不复制完整规范或固定插件缓存路径。

设计与计划保留目标和必要依据。实现进度、当轮讨论和重复日志不混入使用指南；有必要保留的接入差异及验收结论使用已有合适位置，不为每次工作新建一份流水。

## 元数据、导航与生成资料

包描述、首页介绍、页面 title/description 和 README 使用一致的概念，文字长度按各自展示场景调整。先核对实际能力，不用“闭环”“平台级”等宽泛词代替功能说明。

共享文件从维护源更新；API、LLM 文档和索引按当前公开类型、注释或 Markdown 生成，不手改输出或重复维护接口。文档站的导航、地址与页面检查见[文档站](website.md)。
