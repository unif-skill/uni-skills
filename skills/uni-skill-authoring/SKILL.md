# 编写与审查 Agent 技能

从任务和工程资料确定谁会使用这项技能、要完成什么、怎样知道做对了。先查已有入口。同一任务的做法在一处维护，有独立的使用场景和交付结果时再新增技能。

## 把材料写成正文

技能正文只写适用场景、操作和必要的判断标准。把使用者需要的入口、版本、权限或限制放在会影响操作选择的位置。

把讨论中已确定的结论写成独立的规则，交代适用条件、做法和结果。删去会话中的指代、会议经过、命名沿革和作者对方案的解释。保留会改变操作的技术事实。例如，解码器仍在读文件时，要写清谁收到读取结束通知、谁可以删除临时文件。

按任务发生的顺序组织内容。用目标读者熟悉的语言和准确的动词，让人找到要读取的对象、要执行的操作和预期结果。中文正文使用自然直白的中文。

标题说明读者要完成的任务，正文按信息之间的关系选择写法。

| 信息关系 | 合适写法 |
|---|---|
| 说明单条规则、条件或原因 | 用短段落写清适用对象和结果。 |
| 按任务查入口、按条件选做法或并列比较 | 用两列或其他便于查阅的短表，一行一项。 |
| 操作有先后顺序 | 用编号步骤。 |
| 各项条件可以独立检查 | 用列表或检查清单。 |
| 命令或样例可直接复制 | 用代码块，保留必要上下文。 |
| 多方关系或流向难以用文字讲清 | 用小图标出参与方和方向。 |

只选对当前任务有帮助的形式，把模型口令、缩写串和堆在一起的关键词写成有明确对象的句子。

## 设置触发入口与资料

用一两句自然的话写 `description`，说明谁遇到什么任务时会选它。用一个可判断的条件分开容易混淆的邻项，把具体步骤和检查放在正文。展示摘要和默认提示指向同一任务，自动选用策略按既定调用方式设置。

一个任务保留一个可调用入口。专项技能保留本平台或场景特有的判断，其他技能仅在组合任务中按需选用。自身必读的协议、模板和脚本随技能目录分发。共用资料可按正式机制从单一来源生成，并在分发前核对一致性。插件安装指引放在接入文档，维护分工和生成流程放在仓库维护入口。

## 从维护者的视角验收

单独打开最终技能和必要资料，代入未参加讨论的维护者，自查能否从中读出何时使用、从哪里开始、随后怎么做、怎样判断完成。若必须回头询问某个代词、旧方案或作者意图，改写相应句子。有独立读者时，也可只给最终材料，请对方按实际任务试读。

逐条核对原始依据，包括错误、取消、并发和资源责任。保留每项约定的适用范围。某种失败有规定的回执，只在该条件下写这个回执。材料尚未定义的默认值、兼容方式或失败结果，只有影响当前操作时才标明待核实。

只读技能名称和描述，用一个应选的任务和一个容易误选的任务试选。若仍须翻正文才能分清，先改描述，并对照界面摘要核实用词一致。

单独取出完整技能目录，核对引用、展示元数据和声明的资产。规则变化时，用实际材料检验执行结果。格式校验、模型发现、读取记录和任务完成各自报告实际证据。
