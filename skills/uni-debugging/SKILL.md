# 定位故障并验证根因

先确定哪项操作、哪个版本和环境出现什么现象，用户期待的结果来自哪份契约。保留一次失败的原始输入、时间、关联标识、必要错误码和已经发生的副作用；示例、日志及报告按项目约定脱敏。明确本次要求是解释、复现还是修复。

## 从现象追到失败位置

1. 从用户或调用方实际使用的入口复现，保留正常对照。记录输入、时序、身份、配置、依赖和执行结果。间歇故障尽量控制一次相关事件的顺序，例如先挂起回执，切换账号，再释放回执。无法复现时列出已观察事实和还缺哪一项证据。
2. 沿调用链核对每次交接的输入、预期和实际输出，追到第一次偏离契约的位置。跨进程时核对实际运行的修订、路由和依赖，按同一操作关联上下游记录。界面提示、外层状态码或最后一条日志通常只能定位表现层。
3. 对能解释现象的原因，选择可区分它与其他解释的最小检查。例如同一请求在本地与目标环境分别读取了哪个配置，旧回执处理时仍绑定哪个实例。每次只改变相关条件，核对结果与正常对照。调查回归时对照最后正常和首次失败版本，区分提交变更、运行配置与工作区差异。
4. 指出可定位的责任代码、配置或依赖，以及触发条件、传播到用户的路径和证据。证据只到某个边界时说明尚不能判断的部分和下一项有区分度的检查。对第三方缺陷核对实际包版本、公开修复和已发布产物，按库内缺陷或宿主接线确定归属。

## 已授权修复

在根因所在位置做满足契约的最小更改，保护已有数据、其他有效操作和原错误语义。有副作用的写入先核实第一次的实际结果及幂等条件，再判断能否重试。

按原版本条件和真实入口验证修复后的结果，同时跑正常对照及受影响的取消、失败或恢复路径。只读诊断交付证据、结论与缺口。发布、部署和外部反馈各按对应授权执行。
