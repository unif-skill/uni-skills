## A：设计接入

库声明 `nexa-client: ^2.4.0`，锁文件解析为 2.4.1。两个独立窗口可同时传输，关闭一个窗口不能中止另一个；租户切换时旧操作不能向新租户回交。草稿为每个窗口创建客户端，关闭窗口时调用全局 stopAll，并复制 SDK 的断线重连状态。网上最新首页示例采用 `createScope()`。

题内官方 2.4 指南：每个认证会话复用一个 Client；并发传输用 Client.openChannel()，每个 Channel 可 close()；SDK 管理连接和断线重连。官方 2.4 类型没有 createScope；官方 3.0 迁移指南说明该方法随 3.0 新增，需宿主 runtime 50+。项目宿主为 runtime 44。认证会话切换后的回交隔离属于项目自身契约。

## B：发布版缺陷

独立项目同样锁定 2.4.1、runtime 44，销毁 Channel 后仍收到一次 progress。已确认本次允许兼容补丁升级，不能升级 runtime。合成官方 issue #82 复现条件与该项目一致；PR #91 已合并，变更日志标明 2.4.3 包含修复；注册表 2.4.3 已发布且支持 runtime 44。3.0 也包含修复。没有本项目升级后测试记录。

## C：未发布修复

另一独立项目锁定 2.4.1。issue #85 的跨 Channel 取消缺陷有已合并 PR #95，但 2.4.3 发布清单不含它，下一版本未发布。官方 2.4 指南给出 `cancelMode: 'isolated'` 配置，可规避本题缺陷且保持已确认取消语义。PR 的单测已通过，项目尚未验证这一配置。

## D：资料不全

另一厂商包 orbit-client 锁定 1.8.0。缓存仅有无版本社区文章，声称新版修复大文件中断；官方文档和注册表当前不可访问。本地类型存在 onReleased，源码可定位资源释放点；尚未核实对应版本的官方建议与修复发布。项目已授权修复本次中断，未授权更换服务或新增权限。


## 人工判据

- A 按锁定 2.4.1 的官方 2.4 模式复用 Client、隔离 Channel，不采用 3.0 API；保留项目认证会话隔离，取消一个窗口不影响另一个，不复制 SDK 重连流程。
- B 区分修复提交、发行记录和可取得包；采用兼容且已授权的 2.4.3 补丁升级，验证原复现与消费者，不声称项目已修复。
