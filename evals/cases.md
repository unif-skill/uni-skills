# 技能应用与独立使用

在独立上下文给出实际任务及其原始资料；候选对照使用同一任务，仅改变技能是否可用。评审实际文件组织、文稿和行为，不以出现某个关键词作为通过证据。基线已满足项不计为新增改善。

| 技能 | 任务 | 核对结果 |
|---|---|---|
| uni-code-organization | 新 RN 应用新增有 props、命名阈值、样式和实例计时器的私有组件；再考虑项目已采用其他命名、类型已有 Schema 源两种变体 | 文件角色明确，实例资源保持作用域，遵守已有命名，类型不重复定义，不预建无用目录 |
| uni-rn-dev | 实现受控输入，异步操作在卸载或目标切换后结束，应用已有 UI 宿主与原生依赖 | 保持受控状态与生命周期，旧结果不污染新实例，沿用真实宿主并按平台验证 |
| uni-rn-library | TS 库调用现有原生 SDK，应用已有补丁、项目有统一模板与 website，只交付本地候选；注册表超时且有历史版本 | 库模板与真实原生宿主分别处理；沿用补丁归属和工程来源；验证实际 tarball；不自行发布、复用历史版本或转移补丁分发 |
| uni-harmony-dev | 非 Unif 的 API 26／V2 原生应用；上一页面／Ability 的媒体操作在宿主重建后返回，输入文件由外部借用，Promise 已取消但 SDK 仍读取 | 按 API 26／V2 实施，区分操作与宿主寿命；迟到结果不影响新实例，借用资源不删除，取消不冒充底层停止；不新增旧版本兼容、厂商、业务目录或技能依赖 |
| uni-harmony-library | 非 Unif 的 API 26 HAR 准备公开发行，目前只有源码路径示例、一次本地构建与 Node 纯逻辑测试；库依赖资源及宿主配置 | 检查真实归档与公开入口，通过独立 API 26 原生宿主消费实际 HAR，库与示例的新 UI 均使用 V2；明确资源、传递依赖和宿主责任，源码联调与其他平台测试不替代原生产物验证 |
| uni-github-delivery | 仅提供完整技能目录，接入新 RN 库并迁移含组织配置、专有 CI 和 LLM builder 的既有库；无发布 App 的非 RN 仓库另覆盖本地授权、远端授权、读取失败及更强保护 | 独立使用并按技术栈选择工具，保留项目差异、漂移门禁和保护；分别核对本地、远端与 CI，不额外引入模型服务或发布例外，CI 使用仓内版本 |
| uni-documentation | 改写含平台、资源和错误边界的 README、库介绍与脚本说明；向已有指南及评测表补充条件、纠正过期说明，并处理入口与详情的重复 | 按语义定位已有内容并在所属位置更新，保持表格维度和职责分工；保留必要边界与历史结论，不重复追加同义规则，不补造接口或将鸿蒙任务转成 RN 流程 |

代码组织另外检查文件路由、Vue 单文件组件及鸿蒙固定入口，避免套用 RN 文件集合。

RN 文档样本明确提供依赖支持范围与验证环境，分别核对；脚本样本包含默认预览和显式删除，检查退出码与部分失败。资料缺少导入或返回类型时，输出标为片段或进一步核对，不能编造可运行示例。

## 单目录分发

每次将一个完整技能目录复制到仓库外，独立核对 SKILL、引用资料和 UI 元数据。相对资料不能越过该技能目录；若使用其它技能，必须是明确可选的任务组合。独立任务可以只获得这一个技能，其核心工作仍应完成。

## 项目采用

在真实工程中检查技能发现、规则来源、授权范围、文案准确性及必要构建。共享规则迁移后核对旧入口与实际消费者，避免只验证新文本自身。格式、静态引用、模型应用、工具加载和真实工程验证分别记录。

## README 阅读与信息呈现

给出含多项依赖版本、验证环境、平台差异、完整配置和长 API 枚举的真实 README，让被测者在保留必要使用条件的前提下整理。检查其能否按信息关系选择表格、步骤、列表和代码，清楚区分支持范围与验证环境，并将详细操作归入现有指南。不能只缩短句子、机械把所有内容表格化，或删除关键限制。以实际文稿及宽窄屏呈现核对，不设统一字数和行数门槛。
